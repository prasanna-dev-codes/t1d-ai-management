## Kaggle versus Colab

**Kaggle is the user-selected first environment to plan to evaluate**, conditional on account access, permitted private dataset use and available GPU quota. Its [notebook documentation](https://www.kaggle.com/docs/notebooks) describes session limits and a 20 GB versioned working-output allowance. Treat `/kaggle/input` as read-only source data; prepare derivatives in disposable working space. Verify current filesystem/input/output quotas in the selected account rather than assume unlimited scratch capacity. Saving a notebook version with outputs is a required persistence step; writing a checkpoint in a running session alone does not prove durable recovery. Keep source data, notebook outputs and model artifacts private unless redistribution is explicitly permitted.

Kaggle GPU quota/availability is dynamic; its [GPU guidance](https://www.kaggle.com/docs/efficient-gpu-usage) describes a weekly allowance that can vary. A listed P100/T4 option does not reserve a GPU or prove its driver supports our proposed Torch build. Check actual device, driver, Python, VRAM, internet/dataset restrictions and remaining quota before the pilot. No quota workaround, keepalive or assumption of a 12-hour uninterrupted GPU session is permitted.

**Colab is the fallback to evaluate** when authorized storage and dataset access fit better. The [official FAQ](https://research.google.com/colaboratory/faq.html) says free resources/GPU types are not guaranteed and runtimes can terminate; free sessions run at most 12 hours subject to availability/usage. `/content` is ephemeral; a saved notebook does not preserve its VM files. A separately approved Drive directory or other persistent store, actual remaining account quota and a successful checkpoint restore test are prerequisites. Drive mounting/account access are user actions requiring an approved destination. No paid tier, background service, SSH workaround or bypass of the notebook interface is authorized.

Neither provider's public docs establish this user's current GPU allocation or persistent storage capacity. No cloud platform is assumed to have supplied one. Dataset access may require terms acceptance, login or permission to rehost; public availability on another site does not authorize platform upload.

## Proposed staged execution and stop conditions

1. **Environment/storage preflight, after provider approval:** use an ordinary interactive free notebook; record the repo revision, Python 3.12, package versions, OS/architecture, GPU model/driver/CUDA/VRAM, current quota and available scratch/persistent/output capacity. `scripts/vision_cloud_preflight.py` provides a metadata-only starting record; its false GPU/rights/storage/training flags must be resolved by human review. It does not provision a runtime or test a GPU. Do not print environment variables, tokens, device IDs or private Git remotes. Test persistence using a small authored text/tensor fixture, disconnect/reopen and verify its checksum; no food data needed.
2. **Rights and sample approval:** name the publisher/release, exact terms, cloud storage permission, attribution, annotation type, reviewed class subset and transfer cap. Pin file hashes. Acquire only the approved sample directly in the cloud; no mirror or automatic local corpus copy. If access/rights or original group lineage cannot be established, stop and document the blocker. The provisional taxonomy cannot be finalized by guessing absent labels.
3. **Quality and grouping:** retain originals untouched; audit corrupt/truncated files, EXIF/modes/dimensions, class coverage, box/mask IDs and exact/near duplicates. Split source meals/sessions and all derivatives together before augmentation. Preserve official test membership; exclude training overlap with official test. Dense/ambiguous duplicate clusters fail for review. Class/group balance and missing source groups are explicit limitations. Freeze manifests, mappings and hashes only after review.
4. **Conditional weights and bounded pilot:** inspect official EfficientNet-B0 and MobileNetV3-Small `IMAGENET1K_V1` provenance/terms; obtain and verify full SHA-256 values, not only filename prefixes. Do not download substitutes. After explicit training authorization, run at most 20 timed batches/10 minutes per model, reset seed/state afterward, and include pilot time in the total budget. Measure loading, augmentation, train/validation speed, VRAM and checkpoint restore. Stop for incompatibility/OOM/unacceptable data loss. There is no automatic paid escalation or local full-training fallback.
5. **Training:** seed 42 first, head warm-up then limited fine-tuning, early stop on validation with patience 3; choose by validation macro-F1/NLL only. At most 10 epochs/model, initially 6 hours/model and 12 hours total across all experiment compute, with a persisted shared budget ledger and shutdown buffer; one GPU run at a time. Log failures and resumed time; restarting a notebook does not reset the budget. Dedicated calibration groups fit temperature/operating points; sealed test never selects a model. Additional seeds/search require budget review. The trainer/checkpoint-resume loop is still to be implemented and qualified in the chosen environment; this proposal does not claim it exists or has run.
6. **Evaluation/export/handoff:** open sealed test only after selection, report support/per-class and aggregate classification/calibration metrics with group uncertainty where defensible, plus authorized blur/lighting/mixed/unknown challenges. Explicitly withhold OOD reliability and detection/segmentation claims without suitable independent annotations/evaluation. Compare the real selected PyTorch model and ONNX graph on identical held-out tensors, record observed drift and local M4 CPU timings. Synthetic graph tests do not satisfy this requirement.

## Compute and storage estimates — planning, not measurements

For `N` training examples, batch `B`, `E` epochs and measured batch time `s`, budget `ceil(N/B) × E × s`, then add validation, calibration, decode/I/O, checkpointing and export. For illustration only, 2,000 examples at batch 32/10 epochs take about **1–11 minutes/model** if batch time happens to be 0.1–1.0 seconds. Allow another **20–60 minutes/model** for setup/evaluation/I/O as an unmeasured planning allowance. These are not promises about either free provider or either architecture. A tiny subset may not support reliable calibration or meaningful generalization; stop instead of inventing results.

A 75,750-example training pool at the same illustrative rate needs roughly **0.66–6.6 hours/model before overhead**; the slower end would break the approved total cap. Full-corpus training is therefore not the initial scope. The timed pilot must replace these assumptions before any sustained run. If the projection exceeds the budget, propose a smaller rights-cleared subset or stop; do not silently reduce evaluation or claim an interrupted run met acceptance.

Reserve **30 GiB free cloud scratch as an initial full-workflow planning allowance**, to be revised from actual archive expansion/cache/environment needs. It is not a demand for 30 GiB on the Mac. Keep checkpoints/ONNX/reports comfortably below Kaggle's published output allowance; the initial export inventory enforces **700 MiB total**, including at most 256 MiB each best/last checkpoint and 100 MiB ONNX. Actual checkpoint sizes depend on optimizer/RNG state. No storage purchase is authorized. Before a later approved local transfer, require at least 10 GiB free plus the verified bundle size; transfer only artifacts, never the corpus. No cleanup is authorized.

## Repository-compatible handoff and reproducibility

Cloud raw/processed data stays in the approved remote store, keyed by source/release and file/manifest SHA-256. Code, approved non-sensitive configs and aggregate review documents belong in Git; real image manifests containing private paths/identities do not. Large binaries and local data are ignored under `ml/datasets/{raw,processed}` and `ml/experiments/artifacts/vision/<experiment>/`.

Prepare a flat export directory with `manifest.json`, `model.onnx`, `evaluation.json`, `class-map.json`, `experiment.json`, `environment.json`, `split-summary.json`, optional `metrics.jsonl`, `best.pt` and `last.pt`. The class map must match manifest order. Experiment metadata must capture data/split/class/preprocessing hashes, source/rights/approval references, exact code revision and resolved dependencies, actual hardware, seed/RNG, optimizer/scheduler, completed epochs/time, selection and calibration roles. Export best and last checkpoints after each epoch and at most ten minutes apart when supported, plus clean shutdown/final artifacts. Verify durable copies and restore identity before resuming; use an interrupted-run marker if persistence cannot be proven.

The dataset-independent scripts are available now:

```sh
python scripts/vision_cloud_preflight.py --output environment.json
python scripts/vision_artifact_bundle.py /approved/export/root --write-index
python scripts/vision_artifact_bundle.py /approved/export/root
```

These commands do not download, train, upload, extract archives or execute checkpoints. Bundle checks enforce allowlisted filenames, size/path constraints and SHA-256 consistency; they do **not** prove legal rights, correct metrics or trustworthy pickle contents. Never load an untrusted checkpoint; a future approved loader must use trusted provenance, `weights_only=True`, bounded tensors and experiment-identity checks. Keep credentials outside the export, use platform secret facilities where later approved, and clear notebook outputs of private details before sharing.

Separate optional `train-cpu` dependencies select the CPU wheel index on Linux x64 for future engineering checks; `train` does not force CPU wheels on a GPU cloud host. Neither extra is cloud-qualified yet. Do not replace a provider's preinstalled CUDA stack blindly: validate Python 3.12, driver/wheel/operator/export compatibility, then freeze the environment actually used. If the provider cannot run the pinned candidates, revise the exact environment transparently before training. No installation claim substitutes for native compatibility tests.
