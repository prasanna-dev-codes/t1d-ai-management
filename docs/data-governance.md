# Phase 02 synthetic research governance

Only authored synthetic engineering fixtures are authorized. Pseudonymization is not anonymization; no real patient identifiers, medical records, datasets, linkage keys or legally valid consents are supplied. Existing safety/privacy policies and required external review continue to apply.

Patient has an opaque study-local research reference and status, with no name/email/date of birth. ResearchStudy is the tenant boundary. ConsentRecord is an append-only versioned control record; the highest currently effective version must be granted and unexpired. AccessGrant binds authenticated actor to study/patient, read/write flags and expiry/revocation. Write implies read. Missing, expired, revoked, suspended or foreign scope fails closed. Synthetic consent is test metadata, not legal authorization. No end-user grant/consent provisioning routes exist.

Runtime reads require current consent/read grant; writes also require researcher/clinician role and write grant. Trusted transaction-local principal/study/patient settings are applied by server code, then service/repository access checks and forced RLS. A forward migration also removes direct internal chunk privileges, including future chunks on insertion; readiness detects unexpected chunk ACLs. Patient row locks synchronize processing with consent/grant changes. Database administrators, migration owners and holders of runtime database credentials are trusted operational boundaries: RLS cannot authenticate identity or resist a compromised server that can impersonate another valid context. No production IdP, deployment authorization or browser login is invented.

`t1d_runtime` cannot own tables, bypass RLS, create databases/roles, alter schema, mutate grants/consent or update/delete/truncate clinical records. Runtime readiness rejects unsafe role privileges, extension versions or migration head. Privileged bootstrap/migration access is separate, loopback only, with distinct ignored mode-0600 credentials. Local Docker storage is not evidence of encryption at rest, audited backup security or clinical compliance. No object store is configured.

Audits are protected structured records: actor, action, scope when trusted, time, correlation ID, result, source reference and revision/resource UUID. Ingestion/correction/read/replay and consent/grant changes are audited without raw payloads or credentials. Consent/grant SQL triggers audit privileged changes. Rejections roll back the clinical transaction and use a separate fixed-category failure-audit transaction; untrusted failed scope is not persisted. If the database itself is unavailable, only the redacted `audit_unavailable` operational event can be emitted. No durable external audit sink is claimed. Denial audits have no patient scope and cannot be browsed through the patient audit endpoint.

Event/revision/audit/consent/batch/outbox records are append-only for normal runtime operations, with defensive update/delete triggers. Superusers can disable protections, so this is not tamper-proof regulated storage. Before regulated use, require an independently controlled audit export, individual privileged-admin accountability, access review, encryption/key management, incident response, backup/restore validation and a jurisdiction-specific assessment. No certification is claimed.

No automatic retention, TTL, deletion, compression or destructive reset is enabled. Withdrawal blocks access; legal erasure, retention exceptions and derivative invalidation need an approved procedure. Corrections append immutable versions; OutboxEvent records revision references for future invalidation/rebuild, with no worker or downstream index yet. No configured persistent volume is deleted by tests or migration rollback.

The dataset adapter interface carries identity/version/license reference, explicit acquisition/license booleans defaulting false, schema/unit/time mapping versions, pseudonymization namespace, limitations and split manifest metadata. It refuses acquisition authority until both checks are explicit. HMAC pseudonyms require an external ≥32-byte key; no linkage key is committed. This interface is not a downloader or proof of dataset rights. Future adapters must validate reports, subject/time grouped splits, provenance, review data rights and retain authorized manifests before ingestion.

AdapterValidationReport partitions observed records into accepted/rejected/quarantined counts and bounds issues to 100 fixed-code/index entries. Counts and indices are validated; medical payloads, identifiers and arbitrary diagnostic text are not report fields. This is a reusable interface, not an executed external-data import.
